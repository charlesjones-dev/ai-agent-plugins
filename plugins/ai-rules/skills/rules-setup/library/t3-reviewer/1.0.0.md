## T3 Code reviewer

These rules apply when a change needs an independent review by a second model, in a session that has T3 Code's tools.

- Ask the user which reviewer to use. Ask every time. Don't pick one yourself, and don't reuse the answer from an earlier review.
- Before you ask, call `orchestrator_capabilities` and name the providers and models it lists as the choices. `/code-review` is always a choice too.
- The providers configured in T3 Code are the only list of the user's LLM subscriptions. The user adds and removes providers as subscriptions change. Never write a list of providers, models or subscriptions into a rule, a doc, a skill or a plan, and never rule a provider in or out from memory or from an older note.
{{#no-review-bots}}
- No AI reviewer bot runs on GitHub on any of the user's repos. Don't wait for one on a PR, and don't tag a bot (such as `@codex`) to ask for a review.
{{/no-review-bots}}
- Each repo's own rules say when a review runs, for example before a branch lands on `staging`. This section says only how to choose and run the reviewer.
- Run a chosen model through T3 `delegate_task`, with `role: "review"` and `isolation: "worktree"`. The reviewer then reads the committed branch in its own checkout.
- The reviewer gets no conversation history, so give it a full brief: the goal, the diff range (`git diff <base>...HEAD`), what the change does, what is already checked, and the areas to look at closely. Tell it to report only, with no edits, commits, pushes or GitHub comments.
- Check every finding against the source it cites before you act on it. Fix or answer each finding yourself.
- Start each new round with a new `delegate_task` call and a new `clientRequestId`. Its brief carries the first brief, the earlier findings, your answers and any objections still open. Never continue a round in the child thread.
