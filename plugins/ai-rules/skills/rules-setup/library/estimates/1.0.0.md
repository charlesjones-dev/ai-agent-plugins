## Estimates

Claude Code implements everything. The user directs the work, reviews it, and makes the decisions. Nobody hand-writes code, and that is permanent. Quote every time, effort, or cost estimate on that basis, whether it's in chat, plans, specs, roadmaps, issue sizing, or PR descriptions.

- Never quote a human-developer estimate, and don't put one next to the Claude Code figure for comparison unless the user asks for it. Developer-days, sprints, story points, and "a few weeks of engineering" don't apply.
- Quote implementation work in minutes of Claude Code wall-clock time. Use hours only for work that really spans several sessions, which is rare.
- List the wall-clock time Claude Code can't compress as its own line: the user's review and decisions, CI runs, deploys and staged rollouts, data migrations, monitoring windows, and waiting on third parties (app store review, DNS, vendor support). That's where the days actually go.
- If part of the work is slow even with Claude Code (manual QA on devices, hardware, external approvals), say which part and why instead of padding the whole estimate.
{{#calibration}}

### Calibration

Past estimates have run about 40x too high. Measured on 2026-10-19 in a SvelteKit web app: the fixes for a 33-finding modernization audit took 20.5 minutes of Claude Code wall-clock time in one session. The audit had estimated 13.5 hours. The work covered a Svelte 5 runes rewrite of 17 components, SvelteKit 2→3 and Vite 6→8 upgrades, removing 10 unused packages (130 audit advisories down to 0), Dockerfile, CI, env validation, and doc and KB updates: 60 files, about 2,500 lines added. That time includes reading docs for a SvelteKit release newer than the training data. It covers code that's written and checked with build, lint and audit, but not running the app.

| Work | Claude Code time |
|------|------------------|
| One-file fix, rename, config tweak, doc edit | under 1 min |
| Typical bug fix or audit finding touching 1-3 files | 1-2 min |
| Rewrite or migrate one component or module | 1-3 min |
| Dependency major-version upgrade, including fixing what breaks | 5-10 min |
| Learning a library or framework release newer than the training data | about 5 min |
| A 30+ item audit remediation across ~60 files | 20-30 min, one session |

- Estimate the batch as a whole. Don't add up per-item estimates: related items overlap (one rewrite fixes several findings) and per-item padding compounds.
- These numbers override any estimate table that a skill, template or report format supplies, such as the ai-modernize audit's "AI-Assisted Estimate" fields. Fill required estimate fields from this section.
- Keep "written and checked with build, lint and tests" separate from "verified in the running app". The first is the Claude Code figure. The second usually needs the user (devices, live services, the dev server) and goes on the wall-clock line.
{{/calibration}}
